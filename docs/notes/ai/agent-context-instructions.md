# Agent 上下文与指令设计

> 写给「已经有工具 / RAG / Skill 的 Agent」：单靠「神奇 Prompt 句式」已经不够。本篇讲**上下文里该放什么、以什么优先级放**，以及指令与工具描述怎么写才稳。关联：[LLM 基础](/notes/ai/llm-fundamentals)、[Agent Harness](/notes/ai/agent-harness)、[Agent Skill](/notes/ai/agent-skills)、[MCP 与工具调用](/notes/ai/mcp-tools)、[RAG](/notes/ai/rag)、[AI 评测与可观测](/notes/ai/ai-eval-observability)。

## 1. 为什么「Prompt 工程」听起来过时

早期 Chatbot：几乎只有一段 system + 用户话。优化空间主要在措辞。

现在的 Agent：

```
系统硬规则
  + 仓库 AGENTS.md / Rules
  + 按需 Skill
  + 工具定义（名称、参数 schema、描述）
  + 检索到的资料（RAG）
  + 对话/记忆摘要
  + 当前用户任务
```

模型表现更多取决于：**检索是否准、工具是否好用、上下文是否被噪音淹没**，而不是多写两句「你是专家，请一步步思考」。

更准确的说法是 **上下文工程（context engineering）**：在有限窗口里，装配对任务有用的信息与约束。

## 2. 分层：什么进常驻，什么按需

| 层 | 放什么 | 原则 |
|----|--------|------|
| **系统 / 硬规则** | 安全红线、输出格式底线、禁止事项 | 短、硬、可测试；少讲业务流程 |
| **产品人设** | 语气、默认语言、产品边界 | 稳定；别和硬规则抢篇幅 |
| **仓库约定** | 怎么构建、目录、提交规范 | AGENTS.md / Rules；与任务相关再强调 |
| **Skill** | 某类任务的标准步骤 | **匹配再加载**，见 Skill 笔记 |
| **工具描述** | 每个 tool 的用途与参数含义 | 写清「何时用 / 勿用」；比花哨 system 更管用 |
| **检索块** | RAG 命中的原文 | 带来源；控制块数与长度 |
| **对话状态** | 目标、已做步骤、待决问题 | 摘要优于全文粘贴 |

经典「Prompt 技巧」（少样本、思维链）仍然可用，但应落在**正确的层**：例如「输出必须是 JSON」→ 优先用模型/API 的**结构化输出**能力（见 [前端对接 AI](/notes/ai/ai-frontend-integration)），而不是只在散文里求模型自觉。

## 3. 指令怎么写才有效

### 3.1 系统侧

- **可验证**：写「禁止编造 URL；不确定就说不知道并列出缺什么」，优于「请尽量准确」。  
- **冲突时谁优先**：例如「工具结果 > 对话记忆 > 通用常识」。  
- **失败策略**：工具报错时重试几次、何时问用户——写进 harness，不只写进散文。

### 3.2 工具描述（常被低估）

工具 JSON schema 的 `description` 是给模型看的「API 文档」。差描述 → 乱调工具。

好描述通常包含：

1. 做什么  
2. 典型触发场景  
3. 不要在什么情况下调用  
4. 重要参数含义与单位  

### 3.3 Skill vs 长系统提示

把「如何开 PR」「如何排障」写成 Skill，而不是塞进永远在线的 system——省 token，也减少任务无关干扰（见 [Agent Skill](/notes/ai/agent-skills)）。

## 4. 和 RAG / 记忆的分工

| 手段 | 解决 |
|------|------|
| **更好的检索与切块** | 「模型不知道我们文档」——优先 RAG，而不是把手册贴进 system |
| **记忆 / 状态摘要** | 多轮目标漂移——存结构化状态，而非无限聊天记录 |
| **微调** | 文风、领域口头禅——成本高；多数产品用 RAG + 指令即可（见 [微调](/notes/ai/fine-tuning)） |

一句话：**缺知识 → 检索；缺双手 → 工具；缺流程 → Skill；缺稳定格式 → 结构化输出 / 校验。**

## 5. 评测：别只靠手感

改一版 system 或工具描述后：

1. 固定一组真实任务（含不该调工具的负例）  
2. 看成功率、多余工具调用、幻觉引用  
3. 回归后再合并  

方法见 [AI 评测与可观测](/notes/ai/ai-eval-observability)。

## 6. 迁移清单（从「调 Prompt」到「调上下文」）

1. 把超长 system 拆成：硬规则 / 人设 / Skill / 工具说明。  
2. 检查工具描述是否比 system 还糊。  
3. 知识类问题是否误用「背进 Prompt」而不是 RAG。  
4. 输出格式能走 API schema 的，就不要纯文案约束。  
5. 每次改动配几条评测题。
